\subsection{PX4 Software-Module Suspect Ranking}

The architecture-aware layer maps topic-level SHAP evidence to commit-specific PX4 software-module inspection candidates. Firmware provenance was read from ULog headers. The corpus contained seven firmware commits, and the most frequent commit, \texttt{82aa24adfca29321cfd1209e287eab6c2b16780e}, occurred in 562 of 1389 usable logs; its source tree was selected for static analysis. All architecture-aware aggregate results are recomputed only from matching-commit logs. In the fixed test partition, this restriction retains 14,419 of 34,059 windows (42.3\%) from 561 matching-commit logs and 1,393 of 3,602 ground-truth anomalous windows (38.7\%). Windows from the other six commits are excluded rather than propagated through a mismatched graph.

The source scanner identifies uORB topic occurrences, assigns publisher or subscriber roles using the nearest recognized uORB API hint within a 500-character local context, and converts source paths into module identifiers. An internal consistency check covers all 244 unambiguous same-statement declarations or calls involving the 18 evaluated topics. Within this explicit scope, agreement with the statement-level role rule and recovery of its explicit edges are both 1.000. This is not an independent gold audit because the reference and parser use the same uORB hint vocabulary at different context granularities; it does not quantify recall for macro-generated, indirect, conditionally compiled, or runtime-created relations.

The initial source-tree scan contains 180 edges and 54 modules. A conservative-exclusion sensitivity removes paths containing examples, templates, tests, POSIX, QURT, Bebop, Linux, Snapdragon, simulator, or replay markers for the log-confirmed PX4FMU\_V2 and NuttX environment. The filtered edge list must be a strict subset of the original graph and is checked for evidence conservation. This rule is deliberately path-based: neither the unfiltered nor filtered graph is an actual target-specific compiled build graph. Full exclusion rules and software settings are listed in Appendix~\ref{app:reproducibility}.

For propagation mode $r$, let $\mathcal{M}_t^{(r)}$ be the modules connected to topic $t$ and $E_t$ its topic-level evidence. Evidence is allocated uniformly across the connected modules:

\[
A_{t,m}^{(r)}=\begin{cases}
E_t/|\mathcal{M}_t^{(r)}|,&m\in\mathcal{M}_t^{(r)},\\
0,&\text{otherwise},
\end{cases}
\qquad
S_m^{(r)}=\sum_t A_{t,m}^{(r)}.
\]

Producer-only, consumer-only, bidirectional, topic-only, and random-mapping modes represent different engineering interpretations or controls for the same topic evidence. Uniform allocation can favor or dilute modules as a function of topic degree. A further sensitivity divides each module's aggregate score by its number of mapped topics before renormalization. These ablations are reported rather than treating one propagation rule as uniquely valid. The outputs are commit-level source-tree inspection candidates: they are version-dependent, static, propagation-dependent, and neither causal root-cause localization nor deployment-build validation. Mapping coverage, exclusion sensitivity, evidence conservation, and propagation-mode results are reported in Section 5.2.
